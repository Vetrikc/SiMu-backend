# Нагрузочное тестирование SiMu

Замер сделан на локальном стенде: закрытая модель (fixed concurrency), трафик идёт через API Gateway,
как у реального клиента.

## 1. Методика

- **Профиль чтения**: 55 % `GET /api/v1/music`, 30 % `GET /api/v1/me/playlists`, 15 % `GET /api/v1/users`.
- **Профиль входа**: `POST /api/v1/auth/signin` (BCrypt + запись refresh-токена и аудита).
- Перед замером: 50 пользователей, 106 треков в `simu_music`, прогрев 12 с.
- Лимиты шлюза подняты на время теста (иначе 429 после 20 запросов), после — возвращены.
- Генератор: `scripts/load/simu-load.js` (Node, keep-alive, закрытая модель, C воркеров).

## 2. Окружение

| Параметр | Значение |
|---|---|
| CPU | AMD Ryzen 5 3600, 6 ядер / 12 потоков |

## 5. Анализ

- **Насыщение наступает около 1550–1600 RPS** при C = 32–64: вдвое больше воркеров даёт ту же
  пропускную способность и вдвое большую задержку. Это признак очереди, а не недогрузки.
- **Узкое место — CPU шлюза** (до 3.5 ядер из 12 потоков): на каждый запрос он разбирает JWT,
  делает два обращения к Redis (лимит и проверка отзыва) и маршрутизирует. Redis при этом загружен
  лишь на 17 %, то есть ограничение не в хранилище, а в вычислениях на шлюзе.
- **Второй потребитель — music-service** (1.8 ядра): `GET /music` отдаёт весь список без пагинации,
  сериализация JSON и формирование ответа занимают больше CPU, чем сам запрос к БД.
- **PostgreSQL далеки от предела** (≤ 41 %): пул из 10 соединений на сервис не был исчерпан,
  поэтому увеличение пула на этом профиле ничего не даст.
- **Вход упирается в BCrypt**: 78 RPS при 8 воркерах, средняя задержка 102 мс, auth-service
  кратковременно занимает до 8.4 ядер. Это ожидаемо: стоимость хэша — десятки миллисекунд CPU
  на запрос, и она не параллелится внутри одного вызова.

## 6. Что улучшать по приоритету

1. **Пагинация `GET /api/v1/music`** (`limit/offset` или курсор) и короткий кэш в Redis (30–60 с) —
   снимает основной CPU с music-service и уменьшает ответ с 6 КБ до сотен байт.
2. **Несколько реплик api-gateway** за балансировщиком: шлюз stateless, рост пропускной способности
   будет почти линейным.
3. **Сократить число обращений к Redis на запрос**: кэшировать результат проверки отзыва на 1–2 с
   в памяти инстанса, лимит считать локальным token bucket с периодической синхронизацией.
4. **Реплики auth-service** для профиля входа; при необходимости увеличить `server.tomcat.threads.max`
   (по умолчанию 200 — не является лимитом при 8 воркерах).
5. **Hikari 10 → 20** имеет смысл только после появления нагрузки на запись (создание плейлистов,
   загрузка треков) — сейчас БД не насыщены.

## 7. Как воспроизвести

```bash
# 1. стек
docker compose up -d

# 2. на время теста поднять лимиты в .env и пересоздать шлюз
#    RATE_LIMIT_SIGNIN_PER_MINUTE=1000000 и т.д.
docker compose up -d --force-recreate api-gateway

# 3. пользователи и токены
node scripts/load/simu-load.js prepare 50

# 4. замеры
node scripts/load/simu-load.js run 16 45 reads
node scripts/load/simu-load.js run 32 45 reads
node scripts/load/simu-load.js run 64 45 reads
node scripts/load/simu-load.js run 8 30 signin

# 5. вернуть лимиты
```

Альтернатива — k6 (см. раздел 8 в отчёте о методике) или JMeter; скрипт генератора намеренно
без зависимостей, чтобы запускаться там, где нет k6.

## 8. Ограничения измерения

- генератор работает на том же хосте, что и стек, и конкурирует за CPU — реальная пропускная
  способность выше;
- по одному экземпляру каждого сервиса, без балансировщика;
- отсутствие пагинации делает ответ зависимым от размера таблицы (106 треков в замере);
- сеть Docker Desktop на Windows добавляет накладные расходы, которых не будет в Linux;
- профиль записи (создание плейлистов, загрузка файлов) отдельно не замерялся: он упирается
  в MinIO и диск, а не в изученные узлы.

## 9. Тестовые данные

Создано 50 пользователей `l<base36><i>` и 100 треков `Track N`. Удаление:

```sql
-- simu_music
delete from music where name like 'Track %';
-- simu_auth (каскадом уйдут роли, токены, identity)
delete from users where username like 'l%' and email like '%@example.com';
```
