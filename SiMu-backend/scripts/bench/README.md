# Нагрузочный стенд SiMu (Linux)

Скрипт поднимает весь стек с нуля, генерирует нагрузку, собирает метрики и строит отчёт.
Рассчитан на чистую Ubuntu 22.04/24.04 (или Debian): достаточно Docker, остальное доустановит.

## Быстрый старт

```bash
git clone https://github.com/Vetrikc/SiMu-backend.git
cd SiMu-backend/SiMu-backend
bash scripts/bench/run.sh --repo https://github.com/Vetrikc/SiMu-backend.git
```

Если репозиторий уже склонирован — `--repo` можно не указывать:

```bash
bash scripts/bench/run.sh --workdir /opt/simu --keep-up
```

Полный прогон занимает **25–40 минут**: сборка 5 образов, прогрев, 3 сценария × 3 уровня
конкурентности по 60 с, смешанный профиль и сбор снимков.

## Что делает

1. Проверяет и при необходимости ставит `wrk`, `jq`, `python3`, `sysstat`.
2. Клонирует/обновляет репозиторий, находит `docker-compose.yml`.
3. Генерирует `.env`: случайные `JWT_SECRET`, `INTERNAL_API_KEY`, пароль MinIO; поднимает лимиты
   шлюза до 1 000 000/мин, чтобы не ловить 429 во время замера.
4. Собирает и поднимает стек, ждёт healthy по `/actuator/health`.
5. Создаёт 20 пользователей и 200 треков (данные нужны, чтобы каталог был реалистичным).
6. Прогревает сервис 30–60 с.
7. Запускает фоновый сборщик метрик и прогоняет `wrk`:

| Сценарий | URL | Смысл |
|---|---|---|
| music | `/api/v1/music?limit=50` | каталог (идёт напрямую в реплики music-service) |
| playlists | `/api/v1/me/playlists` | библиотека (через шлюз, кэш Redis) |
| users | `/api/v1/users` | профиль (кэш Redis) |
| mixed | 55/30/15 одновременно | приближение реального профиля |

Уровни конкурентности по умолчанию: 16, 32, 64 (меняется `--concurrency "32 64 128"`).

## Что собирается

```
bench-results/<timestamp>/
├── summary.md              # готовый отчёт
├── wrk/                    # вывод wrk по каждому сценарию + метки времени
├── stats/
│   ├── docker-stats.csv    # CPU, память, сеть, диск по контейнерам каждые 2 с
│   ├── mpstat.log          # загрузка каждого ядра
│   ├── vmstat.log          # контекстные переключения, очереди
│   ├── net.log             # sar -n DEV (если установлен)
│   └── memory.log          # free -m
└── snapshots/<label>/
    ├── prometheus-8082..8085.txt  # Hikari, Tomcat, JVM, кэш, HTTP
    ├── health-*.json
    ├── redis-info.txt
    ├── pg-auth-activity.txt
    ├── pg-music-tables.txt
    ├── kafka-groups.txt / kafka-topics.txt
    └── compose-ps.txt
```

## Как читать отчёт

- **RPS по уровням конкурентности**: там, где перестаёт расти, — точка насыщения.
- **p99**: рост при стабильном p50 означает очередь (пул, Redis, БД).
- **Top containers**: если первым упирается шлюз, а хост загружен меньше 80 % — ограничение в клиенте/сети.
- **Hikari pending > 0** — мало соединений; **tomcat busy ≈ thread limit** — кончились потоки.
- **Redis ops/s** и **Kafka lag** показывают, не стали ли зависимости узким местом.
- **mpstat min idle** — были ли моменты полной загрузки CPU.

## Полезные флаги

| Флаг | Что делает |
|---|---|
| `--quick` | 30 с на прогон, уровни 16 и 64 |
| `--keep-up` | не гасить стек после теста |
| `--light` | остановить реплики (1 шлюз, 1 music) для слабых машин |
| `--users N` | сколько пользователей создать |
| `--duration S` | длительность одного прогона |
| `--concurrency "32 64 128"` | уровни конкурентности |

## Требования

- 6+ ядер, 12+ ГБ RAM, 20 ГБ диска (образы + данные).
- Docker Engine + Compose v2 (не Docker Desktop).
- Для `wrk` на 128+ соединений — `ulimit -n 1048576` (скрипт предупредит, если лимит мал).

## Ограничения

- Генератор работает на том же хосте, что и стек: на слабых машинах он сам становится
  узким местом — смотрите `mpstat` и CPU top-контейнеров, чтобы это заметить.
- `/api/v1/music` идёт напрямую в music-service (без шлюза), поэтому сценарий не проверяет
  проверку отзыва токенов.
- Данные не очищаются: после прогона в базах остаются пользователи `bench*` и треки `Bench N`.
